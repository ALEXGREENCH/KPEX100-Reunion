# Участие в разработке

Reunion развивается как проверяемая модель оригинального исполнения. В изменении
важны конкретный сбой, подтверждённое поведение и способ повторить результат.
Сначала прочитайте [архитектуру](doc/architecture.md) и границы
[совместимости](doc/compatibility.md).

## Подготовка и обычные проверки

Нужны Node.js 22+, npm и, для Python-инструментов, Python 3.11+.
Из корня репозитория:

```sh
npm ci
npm test
npm run format:check
npm run build
```

Эти команды не требуют проприетарных оригиналов. `npm run check` объединяет
проверку оформления, тесты, сборку и проверку готового сайта. Проверка полного игрового
корпуса выполняется отдельно, после локального импорта:

```sh
python tools/assets.py import /path/to/originals
python tools/assets.py verify
npm run test:integration
```

Все исходные ROM/SGS должны совпадать с каталогом. Не заменяйте контрольный
хеш новым только ради прохождения проверки: сначала установите происхождение
нового файла и различие его поведения. Для Python-ядра используйте отдельные
команды из [desktop-инструкции](doc/desktop.md).

## Оформление

- JavaScript, HTML, CSS, JSON и Markdown: Prettier **3.6.2**, `npm run format`.
- Собственные Python-файлы: Black **25.1.0**, отступ четыре пробела.
- UTF-8, LF, завершающий перевод строки; настройки включены в `.editorconfig`.
- Сторонний код и исторические данные не переформатируются автоматически.

```sh
python -m pip install black==25.1.0
python -m black --check tools desktop/kpex desktop/tools desktop/tests desktop/launch.py
```

Вносите небольшие изменения с понятной причиной. Выносите общий код в модуль,
когда он действительно используется в нескольких местах. Комментарий должен
объяснять аппаратную особенность, подтверждённый ABI или необходимый компромисс.
Не маскируйте неизвестный syscall безусловным успешным ответом.

## Ошибка и регрессионный сценарий

Полезное сообщение содержит:

- commit или версию Reunion, браузер/ОС и используемый режим;
- идентификатор игры, SHA-256 ROM/SGS и профиль;
- точные действия до ошибки, ожидаемый и полученный результат;
- сообщение журнала, PC/syscall, если они доступны;
- краткий JSON-сценарий для [replay-sgs](doc/replay.md), если ошибка воспроизводится без UI.

Не прикладывайте ROM, SGS, закрытые SDK или дампы RAM к публичному issue.
Для синтетического примера используйте свои данные. В тесте проверяйте
наблюдаемое поведение: например, правильное событие таймера, результат чтения
файла, счётчик или хеш кадра. Сам факт завершения функции без исключения
недостаточен для объявления игры совместимой.

## Исследования GNEX

Сохраняйте URL, дату документа, точную редакцию, SHA-256 и страницу/адрес,
поддерживающие вывод. Разделяйте описание руководства, реализацию SDK,
реализацию конкретной ARM-прошивки и поведение игры: они могут различаться.

Сырые SDK-файлы остаются локальными. Инструменты `sdk-static.py` и
`sdk-syscalls.py` читают их как данные и не исполняют установщики.
[Инструкция исследования](doc/tools-guide.md) описывает воспроизводимые шаги.
Новые оригиналы не включаются в публичный сайт автоматически.

## Pull request

Опишите проблему и результат, укажите выполненные проверки и оставшиеся
ограничения. При изменении поведения GNEX приложите источник или минимальный
сценарий, подтверждающий семантику. Обновляйте матрицу совместимости только
после содержательной проверки игрового процесса и ввода.

Сохраняйте уведомления сторонних компонентов. Оригинальный код проекта имеет
[MIT-лицензию](LICENSE); условия зависимостей перечислены в
[THIRD_PARTY.md](THIRD_PARTY.md) и не заменяются лицензией Reunion.
