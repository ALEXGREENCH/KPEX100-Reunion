# Отпускание кнопки: SDK и оригинальная прошивка Kingston

6 ноября 2026 года исправлен протокол прямого запуска современных K-PEX
SGS: после отпускания действительно удерживаемой кнопки отправляется
`KEYPRESS 255`. Ранее это делал телефонный профиль и отдельная настройка
Star Fighter, а общий профиль K-PEX пропускал событие.

## Два независимых источника

Статическая цепочка SDK 2.12 записана в
[исходном разборе](../validation/key-release.json): WM_KEYUP проходит через
проверку флага конкретной удерживаемой кнопки, таблицу `0x50F254` и
диспетчер `0x442820`. Современная VM получает `255`; legacy-ветка v1/v2
отбрасывает это значение. Установщик и Windows-программа не запускались.

Отдельный [новый протокол трассировки](../validation/kpex-native-key-events.json)
получен из неизменённой Kingston 2.12 с ранее достигнутым состоянием Hell
Fire. Ввод поступал через `FirmwareMachine.key`, то есть моделируемое
железо. Вызовов прямого `runtime.event` в эталоне нет. Перед наблюдением
проверены SHA-256 ROM, снимка, SGS и загруженного участка байткода.

На входе оригинального ARM-интерпретатора `0x20049298` записаны значения
системной переменной 0: SELECT **20**, отпускание **255**, RIGHT **17**,
отпускание **255**. Выполнены 25 миллионов инструкций полной прошивки.
Это проверка оригинального кода в аппаратной модели, не измерение
физического Kingston.

## Изменение адаптеров

Веб- и настольный адаптеры теперь отправляют событие при реальном отпускании.
Повторный `up` не даёт дополнительного события; оставшиеся удерживаемые
кнопки сохраняются. Ошибочный, закрытый или завершившийся рантайм не
получает новый вызов. Legacy v1/v2 сохраняет фильтрацию.

Четыре кадровых эталона заново записаны **Python/Unicorn**, отдельно от
веб-исполнения, тем же сценарием: START, пять таймеров, начальное нажатие,
40 шагов. Проверены оригиналы по каталогу. Веб-тест сравнивает пиксели,
число событий и все счётчики syscall; исходный аппаратный протокол
дополнительно проверяется отдельным интеграционным тестом.

```sh
node tools/trace-kpex-key-events.mjs ../native-key-events.json
python tools/record-native-key-goldens.py --output ../native-goldens.json
node --test tests/kpex-key-release.test.mjs tests/gnex.test.mjs
```

Оба инструмента требуют новых выходных файлов. Явное `keyReleaseEvent:
false` / `key_release_event=False` оставлено для воспроизведения старых
измерений. Для [прежнего сравнения скорости](web-performance-pass2.md)
используйте `benchmark-web.mjs --kpexKeyRelease legacy`: смена протокола
ввода меняет игровой сценарий и не является сравнением одинаковой работы.

В Battle Armor после исправления повторён сценарий миссии и ещё 600 000 мс
виртуального времени с seed 12345: `idle`, ошибки нет. Сохранённый последний
кадр сценария показывает гараж. Это не доказательство полного прохождения
миссии или устранения всех случайных зависаний, о которых сообщил пользователь.

[Реальный браузерный прогон](../validation/browser-native-release-smoke.json):
65 секунд с исходным Worker, ROM и SGS, 202 down/up-команды, 559 событий
VM и 559 кадров, без ошибки. LCD остался на месте, громкость 40 сохранилась
после выключения/включения звука. Это короткая автоматизированная проверка
ввода и таймеров, не подтверждение устранения редкого зависания.

```sh
node tools/browser-gameplay-check.mjs http://localhost:5173/ ../browser-smoke
```

Playwright и путь к отдельному Chrome настраиваются так же, как в
[проверке интерфейса](web-interface.md). Worker в этом инструменте не подменяется.
