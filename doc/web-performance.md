# Производительность веб-версии

Для режима полной прошивки см. [отдельные прогоны и замеры](firmware-validation.md).

Оптимизация от **5 ноября 2026 года** уменьшает стоимость исполнения оригинальных
игр и задержку показа результата нажатий. ROM, SGS и Swerve-модуль не изменены.

## Что изменилось

1. **Обычные GNEX-события ограничиваются по блокам ARM-кода.** Ранее параметр
   `count` в Unicorn включал проверку каждой инструкции. Постоянный `HOOK_BLOCK`
   watchdog позволяет обходиться без этой накладной работы. Он списывает
   консервативный объём работы `ceil(blockBytes / 2)` и останавливается перед
   блоком, который не укладывается в остаток. Это предел работы, не точный
   архитектурный счётчик инструкций. Явный третий аргумент `event(name, value,
instructionBudget)` сохраняет точный режим и отключает ускорители ROM.
2. **Одна проверенная функция очистки RGB565 выполняется на стороне JavaScript.**
   В Hellfire её цикл занимал около 61% ARM-инструкций исследованного сценария.
   Ускоритель привязан к SHA-256 Kingston 2.12 и дополнительно проверяет байты
   функции и указатель дескриптора. Сохраняются регистры, CPSR/SPSR, память,
   нечётный хвост буфера и учёт пропущенных инструкций. Необычные адреса,
   размеры или выравнивание возвращают исполнение оригинальному ARM-коду.
3. **Для SGS v36 сохранён проверочный режим GNEX VM.** Его модель телефонного
   времени зависит от границ транслированных блоков. Изменение этих границ
   влияло на промежуточные кадры 3D-вступления. Ускоряется отдельный оригинальный
   Swerve ARM-рендерер, а прежний ход телефонного времени сохраняется.
4. **Повторяющийся таймер учитывает время вычисления события.** Полный интервал
   больше не добавляется после завершения обработчика. Новые и перепрограммированные
   таймеры отсчитываются от фактического вызова `SetTimer`, включая его вызов
   в конце долгого START. В одном проходе Worker выполняется один callback;
   между проходами он отдаёт управление очереди клавиш.
5. **Показ кадров допускает до 60 обновлений в секунду.** Прежние 33 мс могли
   превращать игру с таймером 20 мс примерно в 25 отображаемых кадров/с. Кадр,
   временно задержанный ограничением частоты, теперь остаётся ожидающим и
   отправляется при ближайшей возможности, даже если у игры нет активных таймеров.
   Это устраняет задержку картинки после нажатия в статическом меню. Убрана
   вторая лишняя копия RGBA; передаваемый буфер по-прежнему отделён от памяти игры.
6. **Полный запуск firmware не считает инструкции дважды.** Собственный
   аппаратный обработчик уже точно соблюдает `_run_end`; дублирующий Unicorn
   `count` убран. Проверка предела происходит до побочных эффектов периферии.

Чтение и запись отдельных 32-битных значений GNEX также используют готовые
методы CPU без временного массива и DataView на каждый доступ.

## Измерение

[Воспроизводимый benchmark](../tools/benchmark-web.mjs) сравнивает
`fastExecution: false` с обычным ускоренным режимом на одних и тех же оригиналах.
По три парных прогона, один прогрев, 60 явных TIMEOUT и одинаковый ввод.
Монотонные и календарные часы фиксированы. После событий и нажатий сравниваются
хеши кадров; дополнительно проверяются status, ошибки, число событий, syscall
и состояния таймеров. Время вычисления не включает сравнение хешей.

| Игра                 | Ускорение вычисления сценария, медиана |
| -------------------- | -------------------------------------: |
| Hellfire             |                                  3,94× |
| KPetris              |                                  1,89× |
| Ikaria               |                                  1,93× |
| Godori               |                                  2,32× |
| Mu Fairy, legacy SGS |                                  4,62× |
| Independence 3D      |                                  1,61× |
| 1zimae               |                                  3,09× |
| Super Action Hero    |                                  2,16× |

Во всех восьми сценариях проверяемые результаты совпали во всех прогонах.
[Полные результаты и характеристики машины](../validation/web-performance.json).
Отдельный [сценарий Dungeon Fighter на 20 TIMEOUT](../validation/web-performance-dungeon.json)
дал 3,14× с совпавшими результатами.
Это время гостевой работы в Node/V8/WASM, **не измерение FPS Chrome**: отображение,
загрузка из сети, аудиосинтез, игра и компьютер пользователя влияют отдельно.
Benchmark использует явные TIMEOUT, в том числе для невооружённых таймеров,
поэтому является сравнением одинаковых вычислений, а не записью реального
расписания браузера. Изменение Worker-таймеров проверяется отдельными тестами
с управляемыми часами.

Из корня проекта:

```sh
node tools/benchmark-web.mjs --runs 3 --frames 60 --warmups 1 --output performance.json
```

Для проверки конкретной игры:

```sh
node tools/benchmark-web.mjs --games hellfire --runs 3 --frames 60 --output hellfire-performance.json
```

Инструмент требует включённые оригиналы. Неизменённый путь исполнения доступен
исследователю через `GnexRuntime.create(rom, sgs, { fastExecution: false })`;
параметр передаётся и вложенному Swerve. В интерфейсе быстрый проверенный режим
используется автоматически.

## Проверки и оставшиеся ограничения

Дифференциальные тесты сравнивают ускоренную RGB565-функцию с оригинальным ARM
на пустом, нечётном, обычном и нестандартном буфере, включая все регистры,
флаги, соседние байты и границы watchdog. Отдельно проверяются бесконечные ARM
и Thumb-циклы, восстановление после ошибки, точные малые бюджеты, пауза/шаг,
регистрация таймера в конце долгого события и доставка отложенного кадра.
Существующие пиксельные эталоны четырёх K-PEX игр и аппаратные эталоны двух
прогонов по 10 млн инструкций сохраняются.

Длинный синхронный обработчик игры всё ещё задерживает обработку следующей
клавиши до возврата в Worker. Программный ARM-рендеринг сложной 3D-сцены остаётся
дороже 2D, WebGL-подмены нет. Модель телефонного времени использует оценку по
блокам ARM и не является тактово точной. Оптимизация не объявляет все сцены
всех игр работающими с 60 FPS.
